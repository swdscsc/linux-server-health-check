# linux-server-health-check 讲解文档

**先跑一遍再说别的**：

```bash
./src/health_check.sh
```

跑完你应该能看到自己机器的 CPU、内存、磁盘、负载。
**看着输出结果理解每一行的含义**——这是你把它变成自己项目经验的唯一途径。

---

## 一、这个脚本解决什么问题

一句话：**把「人肉巡检」变成「机器自动巡检」**。

不装这个脚本的时候，你发现磁盘满了，通常是因为**服务已经挂了**。
装了之后，你会在磁盘到 85% 的时候就收到告警——这中间差的几天，就是运维的价值。

面试时把这个价值讲清楚：
> 运维的核心不是救火，是**在火着起来之前发现烟**。监控和巡检就是把「事后救火」前置成「事前发现」。

## 二、代码走读

### 1）开头为什么是 `set -uo pipefail` 而不是 `set -e`

```bash
set -uo pipefail
```

- `-u`：使用未定义变量时报错（防止 `rm -rf $DIR/` 里 DIR 为空的惨剧）
- `-o pipefail`：管道中任一命令失败就算失败
- **为什么不用 `-e`**（命令失败就退出）？
  因为巡检脚本**必须跑完所有检查项**。CPU 检查失败不能导致后面的磁盘检查不执行——
  一次巡检要拿到尽可能完整的快照，所以错误要自己用 `alert()` 记录，而不是让脚本中途死掉。

这个取舍面试官很可能会追问，**答出来说明你真的写过 shell，不是抄的**。

### 2）配置用环境变量覆盖

```bash
CPU_THRESHOLD=${CPU_THRESHOLD:-80}
```

`${VAR:-default}` 的意思是：如果 `CPU_THRESHOLD` 没设置就用 80。
好处是**不改代码就能调阈值**：

```bash
CPU_THRESHOLD=60 ./health_check.sh        # 临时收紧 CPU 阈值
export DISK_THRESHOLD=70                   # 或在 cron 里统一设置
```

比把阈值写死在代码里专业得多。

### 3）CPU 采样：两段式求差

```bash
cpu_snapshot() {
  awk '/^cpu /{print $2+$3+$4+$5+$6+$7+$8, $5+$6}' /proc/stat
}

read -r TOTAL1 IDLE1 < <(cpu_snapshot)
sleep 1
read -r TOTAL2 IDLE2 < <(cpu_snapshot)
TOTAL_DIFF=$((TOTAL2 - TOTAL1))
IDLE_DIFF=$((IDLE2 - IDLE1))
CPU_USE=$(awk -v t="$TOTAL_DIFF" -v i="$IDLE_DIFF" 'BEGIN{printf "%.1f", (t-i)/t*100}')
```

`/proc/stat` 第一行 `cpu` 是**开机以来累计**的时间片（单位 jiffies），字段依次是：
`user nice system idle iowait irq softirq steal`

- 第 2~8 列求和 = 总时间片
- `idle + iowait` = 空闲时间片

所以**单次读取只能算开机以来的平均值**，必须读两次求增量才是当前瞬时值。
这就是不用 `top -bn1` 的原因——`top` 首屏给的正是那个滞后的平均值。

`read -r A B < <(cmd)` 这种写法叫**进程替换**，比 `cmd | read A B` 靠谱：
管道里的 `read` 会在子 shell 中执行，变量带不出来；进程替换不会。

### 4）为什么不装 jq 也要出 JSON

```bash
json=$(cat <<EOF
{
  "host": "$HOSTNAME",
  "cpu_usage": $CPU_USE,
  ...
}
EOF
)
```

手写 JSON 的好处：**零依赖**。运维场景经常要在最小化安装的机器上跑脚本，
`jq`、`python` 都不一定有，但 `cat` 一定有。
代价是格式得自己保证合法——所以字段值都做了数值化处理（不会出现 `93.3%` 这种带百分号的字符串混进 JSON 数字字段）。

### 5）退出码设计

```bash
exit $((ALERT_COUNT > 0 ? 1 : 0))
```

这一个字符的设计让脚本**可被编排**：

```bash
./health_check.sh --quiet || curl -X POST 告警webhook
```

## 三、面试问答（必须能答）

**Q：为什么用 Shell 写而不用 Python？**
> 两个原因。
> 一是**部署成本**：Shell 脚本 `scp` 过去就能跑，不用确认目标机器有没有 Python 3、有没有装依赖包。运维场景里你要管几十台机器，这个成本会被放大。
> 二是**职责**：这个脚本本质是调度系统命令 + 文本处理，正是 Shell 的主场。
> 但如果要做复杂的数据分析（比如画 7 天趋势图），就该用 Python——我在日志分析项目里就是这么做的。工具选型看场景，不迷信某一种。

**Q：`df` 显示还有空间，但写文件报 No space left on device，为什么？**
> inode 耗尽。磁盘上每个文件都要占一个 inode，大量小文件（比如日志碎片、session 文件、邮件队列）会把 inode 用完。
> 空间还剩但 inode 没了，一样写不进去。所以我的脚本**同时监控磁盘空间和 inode**，用 `df -Pi` 看 inode。

**Q：负载 2.6 算高吗？**
> 要看核数。负载的含义是「可运行 + 不可中断状态的进程平均数」，
> 8 核机器上负载 2.6 很低，2 核机器上 2.6 就已经排队了。
> 所以脚本里阈值是**动态计算**的：`核数 × LOAD_FACTOR`，而不是写死一个数字。

**Q：脚本跑在 cron 里和手动跑有什么不同？**
> cron 的环境变量极其精简，`PATH` 经常不含 `/usr/local/bin`，所以脚本里调用命令最好写绝对路径，或者在 crontab 里显式设置 PATH。
> 另外 cron 不会加载 `.bashrc`，脚本需要的环境变量得在 crontab 里单独 export。
> 我的脚本用 `--quiet` 模式适配 cron，避免产生邮件轰炸。

**Q：如果让你接入真正的监控体系，你怎么设计？**
> 这个脚本适合单机小规模。机器多了应该上 Prometheus：
> 用 node_exporter 采集指标，Prometheus 定时拉取存储，Grafana 展示，Alertmanager 做告警收敛和静默。
> 我另有一个 docker-monitoring-stack 项目就是做这件事的，可以直接用 docker-compose 起来。

**Q：这个脚本有什么不足？**
> ① 只有单点快照，没有历史趋势，看不出内存是「一直高」还是「突然高」——这是最该补的；
> ② 告警只是打印，没有真正推送（可以加 webhook）；
> ③ 进程只查存活，不看资源占用，不知道是哪个进程吃内存。

## 四、你可以自己动手改的（挑一个，面试有话说）

1. **加告警推送**：`curl` 一个企业微信/钉钉机器人 webhook，把 WARN 内容 POST 出去
2. **加历史趋势**：每次 JSON 快照追加到 `metrics.csv`，用另一个脚本画 7 天曲线
3. **加进程内存 TOP5**：`ps -eo comm,rss --sort=-rss | head -6`，直接指出谁在吃内存
4. **加服务探活**：不只是进程存在，还要 `curl -f http://localhost/health` 确认接口真的能响应
